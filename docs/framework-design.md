# Framework design

Why the project is built the way it is. The README says what it does and how to run it.

## 1. Goals

1. Show security testing a QA team can run on every change: an automated DAST scan (OWASP ZAP) in CI, with clear
   pass/fail rules, plus tests for the vulnerabilities a scanner cannot find.
2. Prove the setup works: a scan that has only ever been clean has not shown it can find anything. The app has a
   vulnerable build with ten planted defects, and each must be reported by the tool named for it.
3. Keep it safe: the vulnerable build must never be reachable from outside.

## 2. The parts

| Part                | Role                                                                                                 | Tools                                               |
| ------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `app/`              | NoteVault: notes with sign-in, search and a JSON API; `--build vulnerable` turns on `app/defects.ts` | Node 24 (runs TypeScript directly), no dependencies |
| `zap/rules.tsv`     | ZAP's rule list with an action per rule: FAIL, WARN or IGNORE (with a reason)                        | OWASP ZAP 2.17.0                                    |
| `scripts/scan.ts`   | starts both builds and ZAP on a private Docker network, runs baseline and full scans                 | Docker                                              |
| `scripts/verify.ts` | judges the JSON reports against the rules and the defect catalogue                                   | Node 24                                             |
| `tests/`            | API security tests (access control, brute force) and unit tests                                      | `node:test`                                         |

## 3. The app under test

- **Hardened build first:** a Content-Security-Policy, frame protection, `nosniff`, a referrer policy, a permissions
  policy, cross-origin isolation headers, `Cache-Control: no-store`; a session cookie that is `HttpOnly`, `Secure`
  and `SameSite=Strict`; an anti-CSRF token in the login form; a new session id after sign-in (no session fixation);
  scrypt password hashes compared in constant time; the same message for an unknown user and a wrong password; at most
  five failed sign-ins per user name in 15 minutes; escaped output; an API that answers 404 for other users' notes; an
  allow-list of editable fields; JSON-only updates; generic error messages; refusal of ambiguous paths.
- **Defects as switches, not copies:** the code asks `has('<defect-id>')` exactly where each defect is planted. One
  code base, so the hardened and the vulnerable build cannot drift apart, and a search for the id shows the line. A
  unit test fails if an id is no longer used in `app/server.ts`.
- **Fixed demo users** with a public demo password: the app only ever runs locally and in CI.

## 4. What each tool catches

| Layer                  | Finds                                                                                                      | Cannot find                                            |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| ZAP baseline (passive) | missing or weak headers, cookie flags, information leaks, anything visible in responses                    | anything that needs an attack or knowledge of the data |
| ZAP full (active)      | injection: cross-site scripting, SQL and command injection, path traversal, and more                       | who may see what                                       |
| API tests              | broken access control (IDOR), mass assignment, missing brute-force limits, session fixation, CSRF on login |                                                        |

ZAP sees what an outsider sees. It cannot know that note 3 belongs to bob, so it cannot tell that alice reading it is
wrong. Access control needs tests written with that knowledge: the OWASP Top 10's first category is exactly that.

## 5. Rules and the decision

- `zap/rules.tsv` lists every rule of both scans (generated by ZAP, then edited). **FAIL** for the rules behind the
  planted defects and for classic high-impact problems (cross-site scripting, SQL and command injection, path
  traversal, weakened CSP). **IGNORE** only with a reason (non-storable content is intended; the session-management
  note is informational). Everything else stays **WARN**.
- ZAP's own exit code only says pass, warn or fail. `scripts/verify.ts` makes the decision, from the JSON reports:
  - hardened build: any FAIL alert, or any WARN alert above Informational, fails the run. A new warning is either a
    problem or a rule that needs a decision; neither may pass silently;
  - vulnerable build: each defect ZAP is responsible for must appear as its expected rule id.
- The verify job writes a Markdown table into the GitHub job summary: per build, per defect, caught or not.

## 6. Isolation and determinism

- **Private Docker network:** `scan.ts` creates `notevault-scan`, runs both builds from the Node Alpine image with the
  repository mounted read-only, and runs ZAP on the same network against `http://notevault-<build>:<port>`. No port is
  published to the host. Containers and network are removed afterwards, also after an error.
- **Pinned images:** ZAP 2.17.0 and Node 24.22.0. A new ZAP version brings new rules and can change results; that
  should be a deliberate update, not a surprise in an unrelated pull request.
- **Spider time limited to one minute:** the app is small; the limit keeps the scan time predictable.
- **Fresh app per API test:** each test starts its own server on a free port, so the brute-force test cannot lock
  out a user that another test needs.

## 7. What the scans found in the hardened build

The first full scan flagged two things in the build I considered finished:

- **Anti-CSRF Tokens Check (20012):** after a failed token check, the error page showed the login form again, but
  with an empty token, a form that could never work. It now shows a link to a fresh form instead.
- **Bypassing 403 (40038):** `/%2e/login` was served as `/login`, because the URL parser removes dot segments. There
  were no path-based access rules to bypass, but accepting ambiguous paths is how such bypasses start. The app now
  answers 400 for any path that is not in its canonical form. The rescan reported the same rule for `/login?`:
  the failed token check answered 403, so ZAP treated `/login` as a protected path and the public login page as a
  bypass. That one was a false positive. The token check now answers 400 (invalid, not forbidden), which is just as
  correct, and the rule stays FAIL so a real bypass would still fail the build. Marking the rule IGNORE would have
  hidden real bypasses too.

## 8. Local and CI

- `npm test`: API security tests and unit tests, no Docker, a few seconds.
- `npm run scan` (about 3 minutes) or `npm run scan:full` (about 9 minutes), then `npm run verify`.
- CI: `checks` → `scan` (matrix: hardened, vulnerable; baseline + full each) → `verify` (downloads both reports,
  judges, writes the summary). The reports stay as artifacts for 14 days.

## 9. What a real setup adds

- An authenticated scan (ZAP context with a login script) so the spider and the active scan reach signed-in pages.
- An API scan from an OpenAPI definition (`zap-api-scan.py`).
- Scans against a deployed test environment with TLS, so HSTS and Secure-cookie rules apply as in production.
- Dependency and secret scanning (SCA), static analysis (SAST), and a periodic manual penetration test. A DAST scan
  is one layer, not a security sign-off.
